# Shopify read-only integration

Current commerce lifecycle and migration 005: [Business-scoped commerce connections](commerce-connections.md).

Anti-Nerd now has a configurable real Shopify installation and read path. It reuses `ShopifyAdapter`, the Action Engine, durable policy/approval/audit repositories and verified Supabase identity. No Shopify mutation, AI vendor, autonomous loop or background sync was added. The development server remains on **localhost:5000**.

Implementation is not the same as an installed store. You must apply the third migration and configure a Shopify app, public HTTPS origin, webhooks and encryption keys before connecting. No real store was contacted during development. Tests use fixture transports and local PostgreSQL (PGlite).

## Your setup: ten steps

1. **Create the app.** Sign into the [Shopify Dev Dashboard](https://dev.shopify.com/dashboard), select your developer organization, open **Apps → Create app → Start from Dev Dashboard**, and name it Anti-Nerd. Keep this existing Next application; do not generate another application. App **Settings** provides the **Client ID** and **Client secret**. See [Shopify’s app creation guide](https://shopify.dev/docs/apps/build/dev-dashboard/create-apps-using-dev-dashboard).

2. **Choose distribution.** Anti-Nerd serving unrelated merchants needs **Public distribution** and Shopify App Store review. Use a development app/store while building. **Custom distribution** is appropriate only for one merchant store or eligible stores in the same Plus organization, not a shortcut to distributing this SaaS to unrelated merchants. Choose deliberately: the distribution method cannot be switched later. Configure a standalone app (`embedded = false`), using authorization code installation (`use_legacy_install_flow = true` in the config template; this flag is Shopify’s name for this install flow, not use of REST). [Distribution guide](https://shopify.dev/docs/apps/launch/distribution/select-distribution-method), [standalone authorization](https://shopify.dev/docs/apps/build/authentication-authorization/authenticate-standalone-apps).

3. **Enter the URLs.** For a public origin such as `https://app.yourdomain.com`, set application URL to `https://app.yourdomain.com/integrations` and the exact allowed callback to `https://app.yourdomain.com/api/integrations/shopify/callback`. No wildcard, extra query or trailing slash on the callback. Configure lifecycle/privacy delivery at `https://app.yourdomain.com/api/integrations/shopify/webhooks`. Copy `shopify.app.example.toml` to your linked app configuration, replace placeholders, and release the app version with Shopify CLI or the dashboard’s version configuration. Never put a client secret in TOML. Release webhook subscriptions too; running Next does not register them. [App configuration](https://shopify.dev/docs/apps/build/cli-for-apps/app-configuration).

4. **Enable only these read permissions:** `read_products,read_orders,read_customers,read_inventory`. Do not enable `write_*` or `read_all_orders`. Keep the app-version scopes and `SHOPIFY_SCOPES` identical. If customer access is not approved, omit `read_customers` from both for an explicitly reduced installation, then reconnect after approval. The customer view handles missing permission without blocking products/orders/inventory. [Shopify scope reference](https://shopify.dev/docs/api/usage/access-scopes).

5. **Copy server credentials.** Copy the app’s Client ID to `SHOPIFY_CLIENT_ID` and Client secret to `SHOPIFY_CLIENT_SECRET`. Keep the already configured Supabase public URL/publishable key and server secret key. The browser never receives the Shopify client secret, token pair or vault key. There is no field for manually pasting a store access token.

6. **Complete `.env.local` and the database.** Apply `supabase/migrations/202609240003_shopify_read_only.sql` after the existing two migrations, using the same SQL Editor or tracked CLI workflow you used previously. Do not rerun the first migrations on your populated database. Set the values below. Generate an independent 32-byte random development encryption key locally with `openssl rand -base64 32`, then place it inside the keyring JSON. Keep `.env.local` uncommitted. Production must load that keyring from your hosting provider’s managed secret store with restricted runtime access, backup/recovery and rotation procedures; setting a flag alone does not provide those controls.

   ```dotenv
   APP_BASE_URL=https://YOUR_PUBLIC_HOST
   SHOPIFY_CLIENT_ID=YOUR_APP_CLIENT_ID
   SHOPIFY_CLIENT_SECRET=YOUR_APP_CLIENT_SECRET
   SHOPIFY_SCOPES=read_products,read_orders,read_customers,read_inventory
   SHOPIFY_REDIRECT_URI=https://YOUR_PUBLIC_HOST/api/integrations/shopify/callback
   SHOPIFY_VAULT_KEYS='{"v1":"YOUR_BASE64_32_BYTE_RANDOM_KEY"}'
   SHOPIFY_VAULT_ACTIVE_KEY=v1
   # Production only, after managed secret injection is actually configured:
   SHOPIFY_VAULT_KEY_SOURCE=managed-secret-store
   ```

   `.env.example` contains the full variable list. These are placeholders, not usable secrets. `CREDENTIAL_KMS_KEY_ID` remains reserved for future AI-provider storage; it does not configure Shopify. Restart `npm run dev` after changing environment variables.

7. **Use HTTPS locally.** For real installation, run an HTTPS tunnel forwarding to `http://localhost:5000`, such as `ngrok http 5000` if ngrok is already installed. Keep the app’s configured port at 5000. Use the resulting public hostname in all URLs above, set `APP_BASE_URL` to that origin, and add the matching `/auth/confirm` redirect to Supabase Auth URL Configuration. Sign into Anti-Nerd **through that HTTPS address**, not a separate localhost tab: the session and secure OAuth cookie must return to the same origin. Next’s additional development origin is restricted to that configured hostname. If the tunnel URL changes, update/release app URLs, Supabase redirects and environment variables together. Disable tunnel/proxy request inspection and query/body logging for auth callbacks. Production requires a stable HTTPS domain and equivalent logging redaction.

8. **Create a development store.** In Dev Dashboard open **Stores → Create store**, choose a **dev store**, and create sample products, inventory and test orders. Use its canonical `name.myshopify.com` address. This is a test installation, not a client-transfer store or live payment test. [Development stores](https://shopify.dev/docs/apps/build/stores).

9. **Test Connect Shopify.** Sign into the correct Anti-Nerd workspace/business as owner. Open **Integrations → Shopify → Connect Shopify**, enter the canonical shop domain, continue to Shopify and approve the read permissions. The return page must say Connected only after verification. Visit Store, Products, Orders, Customers and Inventory (the store navigation links all five). Confirm pagination, an empty list, limited customer access, reconnect and explicitly confirmed disconnect. Check Activity for real connection/read events. Uninstall from Shopify and confirm subsequent reads stop. In Shopify webhook testing, check invalid HMAC returns 401, valid delivery returns 200 only after durable persistence, and repeated delivery has no duplicate effect. Never paste a real callback URL or token into a ticket or chat.

10. **Before public launch.** Complete the selected distribution/App Store review, applicable protected customer-data access approval (including customer/order resources), privacy policy and data-handling requirements. Configure and test all mandatory compliance webhooks and uninstall. Establish the manual privacy fulfillment process below and validate real multi-user/tenant sessions, refresh contention, uninstall/reinstall and key recovery against hosted Supabase and a dev store. No customer names/emails/addresses are requested in this phase. Approval absence can still restrict whole resources; the app shows an honest unavailable/limited state. [Protected customer data](https://shopify.dev/docs/apps/launch/protected-customer-data), [privacy requirements](https://shopify.dev/docs/apps/build/compliance/privacy-law-compliance).

## Lifecycle and security

The Connect POST verifies the same canonical Origin, JSON size/shape, session, current membership/business, owner role and durable rate limit. It accepts a shop domain only, never actor/tenant IDs. A 256-bit state is generated; only its SHA-256 digest is persisted, bound to actor, organization, business, canonical shop, callback, connection generation and a ten-minute expiry. A Secure/HttpOnly/SameSite=Lax cookie binds the browser. Duplicate callback parameters, missing/mismatched cookie, HMAC mismatch, stale timestamp (five-minute tolerance), invalid code/domain and mismatched stored binding reject before exchange. Database consumption is atomic and single use. Reauthorization preserves the same connection ID. Changing an already-bound business to another shop requires an explicit future transfer workflow.

The authorization-code request asks for expiring offline access with `expiring=1`. Access and refresh expiry come from Shopify’s response; no lifetime is assumed. Production refuses vault construction unless managed-secret delivery is declared and a valid keyring exists. The declaration is an operator attestation, not cloud KMS provisioning. Shopify requires expiring offline tokens for new public apps; the current rules and retirement behavior were checked in [Shopify’s access-token reference](https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens).

Tokens are encrypted with Node’s standard AES-256-GCM, fresh 96-bit nonce and authenticated tag. Associated data binds organization, business, connection, reference, purpose (`integration:shopify`) and key version. Ciphertext lives in `private.shopify_credentials`; normal connection rows contain only a reference and metadata. Browser roles and direct service-role table access are denied; narrow server RPCs enforce membership, business and reference binding again. AI purposes cannot decrypt Shopify credentials. The adapter receives only an access token inside the existing credential callback.

Credentials are durably staged while the connection is unavailable. The existing adapter performs its minimal shop query; shop ID/domain and returned permission set are checked, then the verified metadata and connection audit commit. Failure erases staged material and leaves the connection unavailable. A verified shop is bound to a single business globally; an unverified authorization attempt cannot reserve another merchant’s shop permanently.

Refresh begins when access expiry is within sixty seconds. A database lease admits one refresh; concurrent readers fail safely or use the newly committed pair. Both new tokens and expiries commit together with an audit event, under the same reference and a fresh nonce/current key version. A failed/abandoned refresh requires reconnect instead of replaying an uncertain token. Installation is fenced against active refresh/code exchange. Disconnect/generation/lease checks reject stale completion. An in-flight request already sent to Shopify cannot be recalled; disconnect prevents subsequent requests.

For key rotation, inject both old/new key versions on every instance, switch `SHOPIFY_VAULT_ACTIVE_KEY`, and retain old decrypt keys until every surviving record has been refreshed or reconnected under the new version. Inspect only the envelope’s `keyVersion` in the private table. Do not remove an old key while any record or retained backup needs it. Losing an encryption key requires reconnecting affected shops. A future bulk rewrap/KMS service is not implemented. `SHOPIFY_PREVIOUS_CLIENT_SECRET` supports webhook signature verification during Shopify client-secret rotation; follow Shopify’s separate [credential rotation procedure](https://shopify.dev/docs/apps/build/authentication-authorization/manage-credentials).

## Reads, health and disconnect

`lib/server/shopify/service.ts` constructs the existing adapter with the real connection repository and token store, then wraps it with the existing Action Engine and durable stores. UI reads and the authenticated read endpoint submit validated read proposals. Policies can deny or require owner approval. Activity shows an approved read’s minimal result in the response only; another read requires a fresh approval when that policy is selected. Approved live actions remain live; preview actions remain mock. Persisted source and business cannot be switched to obtain another executor. No provider obtains a Shopify transport or token. Live AI remains unconfigured.

`getStore`, `listProducts`, `getProduct`, `listOrders`, `getOrder`, `listCustomers` and `getInventory` use fixed GraphQL documents on **2026-07**, which remains stable per the [version release notes](https://shopify.dev/release-notes/2026-07). Page requests are 20 items; the adapter permits 1–50. Explicit cursors advance one page. No crawling, automatic retries or whole-store ingestion happens. Ten-second timeout, no redirects/cache, HTTP 429 and GraphQL THROTTLED handling bound calls. Throttled responses discard partial data and wait for a later user request; the app does not spend further query cost by retrying. Per-user durable rate limits also apply.

Products show title/status/update date; orders show number/date/payment/total/currency within the permitted history; customers show ID/count only; inventory shows ID/SKU/tracking, without invented location quantities. Results are projected into minimal DTOs and not retained in action receipts/audit. Pages never silently use demo data for a linked store, including a disconnected or broken connection. Other dashboard/AI/ads surfaces remain labeled demonstrations.

Safe health metadata distinguishes Connected, Needs reauthorization, Missing permission, Refresh failed, Disconnected and Error. Customer permission failures preserve other reads. Reconnect repeats the verified flow. Disconnect requires confirmation, deletes local encrypted tokens and pending states, invalidates refresh work and retains audit history. It does not uninstall the app remotely: the merchant can uninstall it in Shopify to revoke Shopify-side access. There is no Admin API mutation or legacy REST Admin revocation added.

## Webhooks and privacy operations

Subscribe to `app/uninstalled`, `customers/data_request`, `customers/redact`, `shop/redact` using the supplied app configuration. The handler verifies raw-body HMAC before JSON parsing, binds the shop header to the signed shop domain, bounds request size and uses a topic/event-time/body digest for durable retry deduplication. Uninstall invalidates credentials/states. Delayed notifications older than the latest connection do not erase a newer install. 401/403 API failures also update connection health; app/scopes_update is not subscribed in this phase.

Compliance receipt is **not automatic fulfillment**. Minimized customer/order/request IDs enter `private.shopify_privacy_requests` with `status=pending`; emails, phone numbers and full webhook bodies are discarded. Email-only customer payloads create a request without customer ID, because Anti-Nerd retains no customer email records. Unknown shops have no retained connection/read data here and return an acknowledgment. Privacy requests for known shops must be reviewed by an authorized operator; there is no notification worker or admin UI yet.

Before public distribution, assign an operator to inspect pending requests daily in the restricted database console, find retained action/audit resource identifiers and any backups, supply the required data or apply an approved deletion/retention procedure, then mark the request fulfilled with a timestamp. Do not disable append-only audit triggers casually: resolve legal retention and data deletion requirements through a reviewed privileged migration/process first. Shopify requires action within its stated compliance window; configure a monitored runbook before accepting public merchants. The queue intentionally does not certify GDPR compliance or claim that app review is complete.

## Troubleshooting

| Symptom                            | Check                                                                                                                                                                            |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Setup pending / 503                | Shopify variables, exact HTTPS origin/callback, valid vault keys, production managed-key declaration. Supabase configuration alone does not activate Shopify.                    |
| Connection information unavailable | Apply migration 003; verify service-only RPC grants and Supabase secret configuration. Do not expose raw database errors to users.                                               |
| Callback failed                    | Same signed-in HTTPS session and active business, correct client secret, configured callback, server clock, fresh one-use link. Start Connect again; do not reuse callback URLs. |
| Connection update in progress      | Wait briefly for the active installation/refresh; abandoned work fails closed and can be reauthorized.                                                                           |
| Already linked                     | A verified store belongs to another business. There is no self-service cross-tenant takeover/transfer.                                                                           |
| Customer details unavailable       | Relevant Shopify approval and read_customers. Reconnect after changing the app’s allowed permission set.                                                                         |
| Reconnect to restore access        | Expired/revoked refresh token, uninstalled app, failed refresh, key missing or changed credentials. Verify deployment secrets without printing them, then reconnect.             |
| Shopify busy                       | Throttling is surfaced; retry later. No immediate retry loop.                                                                                                                    |
| Missing inventory quantities       | Only inventory items/SKU/tracking is implemented; location quantities are a later feature.                                                                                       |
