# Shopify callback readiness failure

The reported `SHOPIFY_NOT_READY / SUPABASE_AUTH_UNAVAILABLE` response came from the callback route's readiness gate, before `requireWorkspace()`, HMAC validation, durable state consumption or token exchange. That gate called `/auth/v1/settings` with a five-second timeout. Any transport error, timeout, non-success response, malformed JSON or disabled email provider collapsed to the same blocker. It was a settings availability probe, not an authentication decision about the returning merchant.

Production request logs on 2026-09-25 showed a successful connect followed by a 503 callback. The failed request had no runtime diagnostic entries. Subsequent production readiness and direct Auth settings checks succeeded. The historical upstream failure cannot be distinguished further from these logs; missing cookies are not established as its cause.

The callback now supplies actual Supabase user/workspace verification to the readiness checker. It still validates all required environment configuration, schema (including migration 005), RLS/permissions, Shopify configuration and vault readiness before code exchange. `requireWorkspace()` still calls `auth.getUser()` and resolves membership and active business through the session's RLS client. A failed verification cannot fall back to an unchecked context. Public status/connect checks retain the settings probe, with one bounded retry for transport failures, HTTP 429 and HTTP 5xx; invalid credentials and disabled email are not retried. OAuth token exchanges are never automatically retried.

## State and browser binding

The browser state cookie remains HttpOnly, Secure, SameSite=Lax, host-only, scoped to `/api/integrations/shopify/callback`, and expires after ten minutes. Supabase SSR defaults are host-only, path `/`, SameSite=Lax; its default options do not explicitly set Secure. The application runs at the configured HTTPS production hostname. A top-level cross-site GET is compatible with Lax cookies. Cookies from a different hostname will not follow the callback. We did not inspect or log live cookie values, and cannot retroactively establish which cookies accompanied the failed request.

The existing private durable state binds the SHA-256 digest of a random nonce to the original actor, organization, business, shop, connection, generation, redirect URI and expiry. The callback validates the browser nonce and Shopify HMAC, then atomically claims the matching state through the existing tenant-scoped RPC before exchanging a code. The verified session context must match the stored state; query-string organization/business values cannot select a context. No state-only authentication fallback or new lookup RPC has been introduced, because the reported failure happened before session authentication and does not justify removing that additional check. Missing/expired sessions require sign-in and a new connection attempt.

The state claim occurs before exchange to prevent concurrent code use. Encrypted candidate credentials remain staged until store verification and atomic commit; commit removes the state. Failures preserve any existing active connection. Existing database tests cover expiry, replay, actor/business binding, replacement rollback and encryption isolation. No live state was consumed or OAuth flow started during this investigation.

Success redirects to `/integrations?shopify=connected`; recoverable failures, including readiness failures, redirect to `/integrations?shopify=failed` with no-store/no-referrer headers and clear the nonce cookie. The protected integrations page may require sign-in. Fixed same-origin redirect paths work even when Shopify configuration is unavailable. Server diagnostics contain only fixed stages, allowlisted error/blocker codes, HTTP status numbers and nonce-cookie presence, never query strings, exceptions, tokens or cookie values.

## Verification scope

Remote `backend_readiness()` returned version 2, ready=true, migrations 001/002/003/005=true, RLS=true, permissions=true and columns=true. The complete `supabase/commerce-verification.sql` is exercised against the migrated PostgreSQL-compatible test database; the remote RPC provides the deployed catalog attestation. Direct remote catalog SQL and private OAuth-state rows are not accessible through the application's restricted API and were not exposed or permissions changed for inspection. The historical state's presence/expiry cannot be independently asserted.

Regression tests exercise the actual callback handler and OAuth service with a cross-site navigation request, verified session, durable-state fixtures, encrypted staged credentials and safe redirects. Failed settings probes, failed real authentication, missing configuration/schema, wrong identities/shop/HMAC, missing cookies, expired/replayed state and secret-free diagnostics are covered. A real post-deployment Shopify approval remains an owner-driven test.
